# 论零信任安全架构设计及其应用

【考点标签】预测题：安全架构（零信任）｜对应考场论述要求：项目背景与职责、架构原则与对比、落地挑战与效果

【摘要】2025 年 4 月至 2026 年 2 月，我参加了某全国性股份制银行开放银行与远程办公访问体系的零信任改造。原体系以 VPN、堡垒机和粗粒度网络分区为主，2024 年发生越权访问和横向移动相关安全事件 17 起，已无法适应开放 API 与远程办公并存的现状。本人作为系统架构师，负责零信任总体架构设计与分批迁移规划，协调安全、基础设施和应用约 40 人实施。架构以身份为中心，建设统一身份、设备健康证明、策略决策点与执行点，并在服务间实施默认拒绝的微分段。首批 186 个应用完成切换后，同类安全事件清零，红队演练中的横向移动全部被阻断，策略决策时延 P95 控制在 40 毫秒以内，远程接入额外时延 P95 不超过 80 毫秒。本文从项目背景、架构原则、落地过程与关键问题等方面论述零信任架构的设计与应用。

## 一、项目背景与本人工作

该行员工约 2.8 万人，开放给合作机构的 API 为 420 个，远程办公峰值并发约 1.5 万。业务上既要让分支机构和外包人员在行外访问内部系统，又要把账户、支付、对账能力以 API 形式提供给合作方。旧体系默认“进了内网即可信”：远程用户拨入 VPN 后即进入较大的网络平面，运维通过堡垒机跳转，服务之间大量明文互调。2024 年全年发生越权访问和横向移动相关安全事件 17 起，其中既有凭证泄露后的内网横跳，也有合作方令牌权限过大导致的数据超范围读取。

2025 年 4 月项目立项，目标是在不中断开放银行业务的前提下，用零信任架构替换“边界信任”。本人担任系统架构师，负责总体架构、策略模型和迁移节奏，组织安全、基础设施、开放平台和应用研发约 40 人实施，并主导了两轮红队演练和架构评审。2026 年 2 月完成首批核心应用切换。

## 二、需求分析与架构难点

业务需求有三项：一是员工、外包和合作机构使用同一套身份访问应用与 API；二是权限按人和应用最小化，而不是按网段放行；三是安全事件可追溯到具体身份、设备和调用链。非功能需求方面：策略服务可用性不低于 99.95%，决策时延不能明显拖累交易，远程办公的额外接入时延 P95 不超过 80 毫秒，方案需满足等保和关基相关要求。

架构难点主要有四点。一是存量系统认证方式不一，核心账务类系统短期不能改造登录。二是安全强度和员工体验互相牵制，每次操作都做强认证会被业务否决。三是若把每条访问都写成独立规则，策略数量会失控。四是东西向流量长期默认互通，微分段一刀切可能误伤批处理和对账链路。

项目还受两个约束：开放 API 的合作方合同不能因改造中断；窗口只有十个月，不能停机做全行级切换。因此迁移必须按应用分批，并保留可回退的旧路径。

## 三、总体架构设计

零信任在本项目中落实为五块能力。身份平面建设统一身份提供者，员工、外包和合作机构主体都映射为可鉴别身份，会话绑定多因素认证结果。设备平面由终端管理出具健康证明，不满足基线的设备不能拿到应用令牌。控制平面分为策略决策点和策略执行点：决策点根据身份、设备、应用、数据级别和行为风险给出允许或拒绝；执行点部署在接入网关、API 网关和服务侧。数据平面对应用流量和服务间流量统一签发短期证书，服务间默认拒绝，只放行显式授权的调用。审计平面记录每次决策的主体、客体、策略版本和结果，供追溯和演练复盘。

与传统边界安全相比，信任不再来自“是否位于内网”，而来自每次访问当时的身份、设备和上下文。VPN 保留为网络可达手段，但拨入成功不再等于获得业务权限。

选型时比较了两条路线。一条是继续加固 VPN 和堡垒机，实施快，但信任模型不变，横向移动问题还在。另一条是全行一次性替换为完整零信任产品，目标清晰，但窗口和存量系统都不允许。最终采用绞杀者路线：新应用强制走零信任，存量应用按业务域分三批迁移，每批保留回退开关。首批覆盖开放 API 和远程办公最集中的 186 个应用。

## 四、关键技术问题及解决方案

1. 存量系统无法改造认证的问题。账务和部分信贷系统只支持旧式口令，项目期内不能改登录模块。解决方案是在应用前放置身份代理，由代理完成统一认证和设备校验，再以受控方式代为建立后端会话；代理不保存长期口令，会话与统一身份审计号绑定。实施后这批系统没有单独开口子，越权访问不再绕过统一身份。

2. 安全强度与使用体验的平衡问题。若所有会话每次都做二次认证，远程办公投诉会直接阻碍推广。解决方案是按风险自适应：新设备、异常地点、访问高敏感数据时强制二次认证，低风险会话在策略允许的时间窗内免二次验证。上线后约七成日常会话无需额外挑战，远程接入额外时延 P95 仍不超过 80 毫秒，业务部门未因体验问题退回旧 VPN 权限模型。

3. 策略数量失控的问题。试点初期曾为每个接口手写规则，两周就积累了难以评审的规则集。解决方案是改为基于属性的策略，按主体部门、设备状态、应用等级和数据分级组合判断，策略以代码方式评审和发布，按业务域拆分所有权。186 个应用切换完成时，策略仍可由各域安全接口人独立评审，没有再出现无人敢改的巨型规则库。

4. 服务间横向移动的问题。内网默认可达，一旦单点失陷就能探测相邻系统。解决方案是服务间通信改为双向认证，网络策略默认拒绝，只开通登记在册的调用关系；批处理链路单独建模，避免误伤日终对账。红队在切换后的域内演练时，横向移动全部被阻断。结合身份审计，2024 年那类 17 起事件在切换完成后的运行周期内没有再现。

5. 策略服务自身成为单点的问题。所有访问都依赖决策，决策不可用等于业务不可用。解决方案是决策结果按会话短时缓存，决策点同城双活，执行点在决策点超时且缓存未过期时按上次允许结果降级，高敏感操作则失败关闭。策略服务可用性达到 99.95%，决策时延 P95 为 40 毫秒，没有因策略平面故障阻断开放 API。

## 五、总结与体会

这个项目使我确认，零信任改的是信任假设，不是再加一层防火墙。第一，身份、设备和权限必须同时成为架构元素，只做多因素认证而继续按网段授权，横向移动仍然存在。第二，迁移要用绞杀者而不是停机切换，回退开关是业务方接受改造的前提。第三，策略必须产品化，没有所有权和评审流的规则库会比漏洞更早失控。不足之处是首批尚未覆盖全部内部管理系统，主机层微隔离仍粗。后续计划用同一套策略模型扩展到剩余业务域，并把数据级脱敏纳入同一次决策。架构评审和红队演练要按批次重复做，不能只在项目结束时演练一次。
