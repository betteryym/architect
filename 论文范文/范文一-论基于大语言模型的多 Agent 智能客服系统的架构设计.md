# 范文一：论基于大语言模型的多 Agent 智能客服系统的架构设计

【考点标签】考点：AI 应用与大模型（Agent／RAG）架构｜对应考场论述要求：项目背景与职责、总体架构设计、关键技术问题与解决

【摘要】2025 年 3 月至 2026 年 1 月，我参加了某大型集团企业智能客服平台项目的建设工作。该项目旨在以基于大语言模型（LLM）的多 Agent 智能客服系统替代传统规则式客服，覆盖售前咨询、售后报障和业务办理等场景。本人作为系统架构师，负责整体架构设计与关键技术选型。系统采用“接入—编排—知识—工具—模型—安全”六层架构，通过多 Agent 任务编排与状态机管理、RAG 混合检索增强、模型网关多路由与降级、Prompt 注入防护等关键技术，实现了日均百万级会话的处理能力。系统上线后，意图识别准确率达到 96%，人工转接率较旧系统下降 62%，P95 响应时间控制在 3 秒以内，并通过了等保三级测评。本文从项目背景、总体架构、关键技术及问题解决等方面对该系统的架构设计过程进行论述，总结了 LLM 应用系统架构设计中的经验与教训。

## 一、项目背景与本人工作

2025 年，集团提出“人工智能＋客服”战略，要求以新技术重构客服体系。旧系统基于 FAQ 关键词匹配与 IVR 语音导航，知识问答准确率不足 70%，高峰期人工坐席不足导致客户满意度持续走低；同时集团旗下多条业务线客服系统“烟囱式”建设，知识库重复维护、口径不一。项目于 2025 年 3 月立项，2026 年 1 月正式上线，覆盖售前咨询、售后报障、业务办理三大场景，注册用户超过 3000 万，日会话峰值约 80 万次。本人担任系统架构师，牵头需求分析、总体架构设计与关键技术选型，组织约 30 人的研发团队实施，并主导了架构评审与性能压测。

## 二、需求分析与架构难点

业务需求方面：一是支持多轮对话与上下文理解，跨业务线提供知识问答；二是能够调用订单查询、报障工单等 20 余个业务系统的工具完成业务办理；三是提供人工接管与转接能力，保障服务兜底。非功能需求方面：高峰并发会话数 1000 以上，P95 响应时间小于 3 秒，系统可用性不低于 99.9%，会话数据满足脱敏、审计等安全合规要求。

架构难点主要有四点：一是大模型推理时延高、成本高，且存在幻觉问题，直接串联调用难以满足响应与质量要求；二是多业务线、多 Agent 协作场景下任务编排复杂，对话状态难以管理；三是工具调用涉及核心业务系统，存在越权与注入风险；四是大模型服务依赖第三方 API，存在限流、故障等不确定性，需要完整的降级方案。

此外，项目还面临时间与成本约束：整体工期十个月，模型调用预算有限，必须通过缓存、降级与模型分级策略控制单会话成本；集团对数据出境有严格限制，核心会话数据必须私有化部署存储，进一步增加了架构复杂度。

## 三、总体架构设计

系统采用六层架构。接入层：统一会话网关，对接 APP、小程序、Web 等多渠道，负责鉴权、限流与会话保持。Agent 编排层：由意图识别、任务规划器（Planner）、多个领域 Agent（售前 Agent、售后 Agent、订单 Agent 等）与工作流引擎组成，将用户请求解析为任务 DAG 并驱动执行，通过状态机管理对话状态，支持断点续跑与人工介入。知识层：知识库统一管理，文档切片后向量化入库，采用 BM25 与向量检索融合的混合检索并经过 Rerank 重排，为生成提供可靠依据。工具层：工具注册中心统一管理外部能力，经 API 网关调用业务系统，执行前校验权限，执行后校验结果。模型层：模型网关对多路模型（大参数公有云模型、私有化部署模型）进行路由、限流、缓存与降级管理，配合提示词模板与上下文记忆模块。安全与可观测层：Prompt 注入检测、敏感信息过滤、全链路审计日志、LLM 链路追踪与成本监控。

技术选型上，微服务基于 Kubernetes 部署，采用 Java 与 Python 混合开发，向量数据库选用 Milvus，消息中间件采用 Kafka，缓存采用 Redis。整体架构将“模型能力”与“业务能力”解耦，使模型升级、业务系统变更互不影响。

在架构设计过程中，我们对两条候选路线进行了权衡：一是纯编排式架构，所有能力通过工作流引擎串联，优点是可控性强，缺点是灵活性与扩展性受限；二是深度自主规划架构，由大模型自行决策工具调用顺序，优点是智能度高，缺点是难以审计和兜底。考虑到金融级合规要求与业务稳定性，最终选择以编排为主、自主规划为辅的混合路线，既保证关键路径可控，又保留了模型灵活应答的空间。

## 四、关键技术问题及解决方案

1. 多 Agent 协作与任务状态管理问题。初期采用无状态 HTTP 服务串联多个 Agent，出现任务中断后无法恢复、上下文混乱、重复应答等问题。解决方案：引入自研轻量工作流引擎，将任务建模为节点与状态机的组合，节点间通过事件总线通信，支持超时重试、断点续跑与人工审批节点挂起；会话上下文统一存储在 Redis 并绑定会话 ID。实施后任务完成率从 82% 提升至 95%。

2. RAG 检索质量与幻觉问题。初期向量检索存在召回不精准、答案引用不可靠的问题。解决方案：采用 BM25 与向量检索加权融合，引入交叉编码器 Rerank 精排，优化知识切片粒度，并在答案中附引用片段供前端展示。实施后知识类问答准确率从 88% 提升至 96%，幻觉率显著下降。

3. 模型依赖的稳定性问题。第三方模型 API 曾发生限流，导致服务抖动。解决方案：模型网关统一路由，高频问答命中缓存，超时自动切换备用模型，全部模型不可用时降级为小参数本地模型并结合规则机器人兜底。实施后即使在模型服务故障期间，系统可用性仍保持 99.9%。

4. 安全合规问题。测试中发现 Prompt 注入与工具越权风险。解决方案：引入 Prompt 注入检测模型与规则双重校验，建立工具调用权限矩阵，实行会话级上下文隔离，全量审计日志留痕。实施后安全事件清零，系统顺利通过等保三级测评。

5. 上下文管理与成本控制问题。长会话中历史消息持续累积，既占用 token 成本又影响响应速度。解决方案：实现会话级上下文压缩与摘要化，超过阈值自动将早期消息压缩为摘要；设置单会话 token 预算与动态截断策略，配合高频问答缓存降低模型调用量。实施后单会话平均成本下降约 40%，长会话响应速度显著提升。

## 五、总结与体会

该项目让我认识到，LLM 应用系统架构设计的核心是工程问题而非单纯的模型问题。第一，评测体系必须先行，离线评测集与在线 AB 实验是模型迭代和质量保障的基础；第二，可观测性建设至关重要，token 成本、链路时延、失败归因都需要全链路追踪支撑；第三，人机协同设计不可或缺，人工接管闭环保证了极端场景下的服务兜底。不足之处在于系统对多模态输入支持较弱，Agent 自主规划的上限仍有待提升。后续计划引入 Agent 反思与长期记忆机制，并建设 Agent 评测自动化平台。同时，我认识到架构评审与压测在 AI 系统建设中同样不可缺位：上线前完成的多轮全链路压测与故障演练，帮助我们提前暴露了模型网关单点风险并完成加固。
